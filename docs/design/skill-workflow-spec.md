# Skill 路由、规划交接与可恢复执行规格

状态：待审阅的实施规格；已获授权产出计划与 spec，尚未开始本规格的实施。

关联：[实施计划](../plan/skill-workflow-plan.md)、[研究全景](../research/upstream-skill-map.md)、[Orca 研究](../research/orca-mechanisms.md)。

## Problem Statement

用户提出新工作时，希望 agent 先查明事实、通过真实访谈澄清决定，再选择合适的研究、原型、规划和实施路径。当前项目主要围绕固定五阶段链编排，存在直接实施入口过宽、部分 skill 只有名称没有执行分支、跨 worker 丢失原始决定、wayfinder 验收阶段混淆、脚本与上游产物不兼容等问题。

已有文档修订尚未形成经行为场景与真实 Orca 演练验证的完整契约；旧测试通过不能证明这些新路径可用。用户不应通过反复提醒才遇到 grill，也不应为了小任务被强制制作整套 spec 和票图。

## Solution

建立以用户意图、未决问题和交付终点为依据的路由，分别决定工作阶段、上下文安排及执行拓扑。以官方 `ask-matt` 为上游路由参考，结合本项目的监督、隔离、授权与恢复规则，逐条标注有意适配。skill 原文负责具体方法，本项目负责如何到达、如何交接、如何验收和恢复。

### 路由与 skill 覆盖

| 输入或触发 | 选择与完成条件 |
| --- | --- |
| 普通解释、状态查询 | 直接答复，不创建 Run；用户要求访谈时进入对应交互流程。 |
| 新想法、计划、设计 | 有工作目录优先 `grill-with-docs`；无工作目录优先 `grill-me`；二者复用 `grilling`。用户明确指定入口时优先遵从。 |
| 已有明确要求的小修复、续跑票 | 核验当前目标、范围、验收和关键决定的来源，可直接 `implement`；记录为何无需重新访谈。发现新取舍后回到澄清。 |
| 规划本身超过一个 session 且路径不明 | `wayfinder`；明确 chart 或 work，不因文件多或实施票多自动建图。 |
| 决定依赖可查证资料 | `research`，引用一手来源；结论回流当前决策，不替用户作决定。 |
| 讨论不足以判断外观、逻辑或状态 | `prototype`，取得用户反馈，记录问题与结论；原型按约定保存在一次性分支。 |
| 决定依赖他人掌握的信息 | `to-questionnaire`，明确接收人和所需回答；回答返回当前澄清/规格阶段。生成文档不授权发送。 |
| 需求已对齐，单 session 可实现 | 同一上下文进入 `implement`，或向隔离执行者交付完整工作说明；无需强制 spec 和拆票。 |
| 已对齐的多 session 实施 | `to-spec` → `to-tickets`；用户核对测试 seam、票粒度和依赖；单票 `implement` 或整图 `implement-spec`。 |
| 外部原始 issue/PR | `triage`，按仓库请求面配置处理；不重复 triage 已由 `to-tickets` 产出的票。 |
| 难复现故障或回归 | `diagnosing-bugs`，先有针对本故障的红反馈；恢复后可进入 `retro`。 |
| 架构痛点、测试 seam 难以建立 | `improve-codebase-architecture`，候选经用户选择后 grill；采用 `codebase-design` 词汇。 |
| 只有用户能完成的操作 | `wizard`，生成经核验的人类操作向导，完成后继续原任务；agent 能做的操作自行处理。 |
| 交付完成、重复失误或流程故障 | `retro`，根据会话一手证据提出环境改进；机械错误优先检查，判断性错误再考虑审查规范。候选不自动扩大当前范围。 |

`domain-modeling` 与 `codebase-design` 为底层能力；`writing-for-agents` 用于维护 agent 文档。`teach`、`wait-what` 保留用户主动选择的辅助入口，不加入每次开发的固定链。实验性 skills 不作为默认依赖。

### 用户参与与上下文

事实由 agent 查证；未决的目标、范围、方案及可观察行为由用户决定。每轮只提出前置条件已满足的问题，等待回答再推进；已有明确授权和相同决定可复用。grill 收口须有用户确认共同理解的证据。

优先在同一规划上下文完成 grill、spec 和拆票。只有工作范围、隔离需求、宿主能力或上下文质量要求跨 session 时才交接。Orca 隔离执行仍遵循项目政策；保留上下文不等于允许在主分支直接编辑。工作阶段不再机械对应一个新 worker。

交接记录保存目标、交付终点、用户原话与决定来源、数值及否定约束、已查事实、未决问题、适用 skill 与依赖、产物指针及下一步。已有文档用指针引用，原始用户决定须可追溯。`handoff` 在跨 harness、目录、协作者或中途分叉时提供可移植交接；普通紧凑子任务可用上下文指针，不额外套完整流程。敏感内容保持去敏。

### Wayfinder 生命周期

1. Chart：先通过 grilling 和领域建模明确 destination，再广度识别决策与 fog。创建地图与可描述的类型化票，先建票再连真实依赖；研究可在授权范围内后台并行。建图完成便收口，不要求所有决策票完成。
2. 若没有 fog 且单 session 可容纳，向用户说明并选择较轻路径，不强制建图。
3. Work：先认领指定票或首个可领取 frontier，按标签处理。每 session 最多解决一张非 research 票；research 可并行。grilling、prototype 是 HITL；research 是 AFK；task 按前置操作决定。
4. 逐票完成须写 resolution、关票、更新地图指针和新票/fog。task 可完成解除决策阻塞的前置工作；不等于直接实现目的地。
5. 地图完成要求所有范围内决定已解决，且无未解决 fog。frontier 空但仍有已领取/阻塞票时不能收口。
6. 通常从完成地图进入 `to-spec`，综合其链接的决定后再拆实施票；若确实变为小工作，附依据选择直接实施。默认不将决策票当实施票。

地图和票遵循仓库 tracker 约定；有原生依赖时使用原生依赖，无此能力时使用已记录的 fallback。HITL 决定不得由 coordinator 模拟。

## User Stories

1. 作为提出新需求的用户，我希望看到应澄清的决定，以便发现隐含假设。
2. 作为用户，我希望小改动按已有清楚指令执行，以免重复回答同一问题。
3. 作为用户，我希望知道为何跳过某阶段，以便审阅执行依据。
4. 作为用户，我希望先讨论 UI 或状态原型，以便对具体结果反馈。
5. 作为用户，我希望资料研究能并行进行，以便继续处理不依赖它的决定。
6. 作为用户，我希望大范围未知问题保存在地图中，以便跨会话继续。
7. 作为用户，我希望建图交付能独立结束，以免未决票被误判失败。
8. 作为用户，我希望已领取或阻塞票可见，以免地图被错误标为完成。
9. 作为用户，我希望他人才能回答的问题形成问卷，以便收集缺失信息。
10. 作为用户，我希望只有我能做的操作有清楚向导，以便解除阻塞。
11. 作为执行者，我希望交接保留原始决定和限制，以免新上下文改写需求。
12. 作为执行者，我希望知道所需 skill 及其依赖能否加载，以免只读包装器便自称完成流程。
13. 作为执行者，我希望临时研究/原型采用合适交付方式，以免误合入产品。
14. 作为协调者，我希望续跑依据实际选定的流程，以免补跑不适用阶段。
15. 作为协调者，我希望旧台账歧义被标明，以免把历史成功当成当前成功。
16. 作为协调者，我希望真实上游票据能被检查，以免有效产物被误拒绝。
17. 作为维护者，我希望中英文执行语义一致，以便两个安装包行为相同。
18. 作为维护者，我希望复盘形成可验证改善，以免同样流程错误反复出现。

## Implementation Decisions

### 工作路由与执行边界

A/B/C 暂保留为交付/监督通道，阶段由路由结果独立标明。路由记录包含意图、入口证据、当前阶段、交付终点、上下文安排、执行拓扑、适用门禁及未决问题。`ask-matt` 作为设计依据，不要求每次自动调用这个用户入口。

工作说明、产品 spec、决策票、实施票须区分。没有产品 spec 不阻止委派 grill；没有授权不触发 tracker 发布、外部消息、真实账户变更或 PR 合并。生成规格和本地任务计划本身不宣称已完成 `to-tickets` 发布流程。

用户调用型与模型调用型 skills 根据当前宿主能力解析；包装器和实际依赖分别确认。无法调用时只在宿主允许时按文件加载其指令，并标记为本项目适配；不可用时报出能力缺口，不声称执行成功。setup 的隐式触发政策须与此一致，不能只凭绝对路径绕过宿主限制。

### 流程记录与续跑契约

流程记录是台账之外的显式、版本化工作计划：保存 Run、目标/授权终点、阶段节点与依赖、适用门禁、状态及来源指针。节点有待处理、执行中、待用户、受阻、已验收、不适用、失效状态。不适用须有入口依据；待用户不是执行失败。

新版续跑接受显式流程记录，输出当前待处理节点、阻塞原因与证据缺口。多个节点可就绪时列出就绪集合；不凭门禁同名跨任务认定通过。已验收节点须绑定具体节点、任务/attempt、产物版本和验收证据。整条流程完成只指授权终点内所有适用节点完成，不等于自动获准合并。

旧台账保持可读、不改写：缺显式流程时仍可提供带 `legacy` 标识的旧链建议，但不得自动派活或宣布新流程完成。证据存在冲突、缺归属或无法验证时输出不确定及需补的证据。撤销、规格变化和产物更新以追加记录使相关节点及下游失效；复用外部/前次 Run 产物须显式导入来源、版本和核验结果。禁止将任意历史通过的 G-docs 推导成当前 grill 已完成。

Wayfinder 的地图事实以 tracker 为权威，本地流程只记录 chart/work/地图完成及证据指针。旧台账 schema 的迁移在兼容设计后实施；禁止直接给现有封闭字段塞入未经验证的新值。

### 产物检查契约

检查入口明确区分产品规格、单张本地票、单张 issue 正文、合并票清单及票据集合；保留旧调用的明确兼容模式。不能无歧义识别格式时要求指定格式，不能默默猜。

单文件票按文件边界识别，issue 正文按验收章节识别，合并清单按约定票边界识别；普通章节不是票。检查空验收、缺引用、无效阻塞与环时分别给出具体票和错误。外部 issue 必须先取完整正文，网络不可达不能当空票。

上游原生格式校验与本项目调度附加项分开报告：上游规格未包含测试档，不等于上游规格无效；进入本项目实施前仍须补齐适用测试范围、验收和任务契约。脚本只检查格式及可确定关系，不评判需求正确性或代替用户确认。

### 交付与验收

每类工作定义输入、真实动作、完成证据、回流位置及交付方式。G-docs 验对齐；G-wayfinder 区分 chart、work、map-complete；规格、拆票、实施及合并继续使用现有门禁并校验适用性。临时研究和 prototype 可用一次性分支与指针；产品改动仍按授权走 PR、review、CI、Merge Danger 与收口。

Orca 使用版本匹配指南和帮助，区分逻辑待答与调用阻塞；普通 ask、同步等待及恢复按实际能力执行。wrapper 加载、worker ready、worker_done、产物验收、合并、tracker 关闭分别记录，不能相互推出。看板只投影显式状态，不成为执行权威。

## Testing Decisions

**Test tier: wide — 同时改变入口、台账归属、产物校验与双语指令，需全量回归。**

优先通过现有 CLI JSON 输出、临时台账/票文件和用户可观察对话验证；沿用现有 chain、ledger、package 与 runtime contract 测试入口，减少仅为测试拆出的接口。新增公共接口须先给失败样例与预期输出。此处为推荐测试 seam，实施前审阅其能否覆盖真实行为。

| 验证层 | 必需覆盖 |
| --- | --- |
| 确定性 CLI/契约测试 | 流程分支、授权终点、节点归属与失效、旧台账、不确定状态、所有产物格式、错误与退出码。 |
| 双语包检查 | 引用可达、脚本字节相同、入口大小、泄漏扫描、scenario 对齐。 |
| Agent 场景评测 | 新需求是否 grill、真实用户确认、skill 依赖、chart/work、问卷/wizard 回流、handoff 保真、授权边界。静态关键字检查不替代评测。 |
| 受控 Orca 演练 | 真实 ask/reply/唤醒、worktree、worker_done、chart 和逐票证据；固定 CLI 版本与宿主能力。mock 通过不称 E2E 通过。 |

### Acceptance criteria

- AC01：给新需求、明确小修复、有效旧 spec、失效旧 spec，分别得到可解释入口，未决取舍不被静默代答。
- AC02：显式选择 grill-me/grill-with-docs 后记录对应依赖加载与真实问答，用户确认前不进入依赖该决定的实施。
- AC03：同一规划上下文或完整交接均可追溯所有关键用户决定；数值、否定条件和未决项不丢失。
- AC04：chart 在地图和研究交接完成时可独立交付；一张未决票不使 chart 失败，也不代表地图完成。
- AC05：work 先认领、按类型处理、resolution 后关票和更新地图；HITL 有用户参与，单 session 非 research 不超过一票。
- AC06：native/fallback 都能正确识别真实依赖，frontier 空但有阻塞、已认领或 fog 时不宣称地图完成。
- AC07：research、prototype、questionnaire、wizard 均有输入、证据及回流；未授权的发送、账户和合并动作不被触发。
- AC08：显式流程续跑只选适用节点；设计-only、单票、多票、wayfinder 和复用 spec 可在各自授权终点正确结束。
- AC09：旧账本可读，歧义、冲突或缺归属得到 legacy/不确定状态；旧 G-docs 不能证明当前 grill。
- AC10：撤销、改 spec、改产物使相关节点及下游失效；不同任务或旧 attempt 的成功不覆盖当前失败。
- AC11：原版本地票、issue 正文、合并票和集合均按真实票边界检查；空验收、环、缺 blocker 有定位错误。
- AC12：规格原生格式与调度增补项分别报告；校验结果不冒充用户批准或需求正确性判断。
- AC13：外部 triage、架构治理、retro 有独立入口；不重复 triage agent-ready 票，不自动实施复盘候选。
- AC14：两语言包在相同场景下选择等价路径；脚本与静态资产保持字节相同。
- AC15：目标 CI 矩阵全量检查通过；真实演练有去敏、可追溯记录，未演练分支明确标记。

## Out of Scope

- 安装所有上游 skills、自动更新用户全局配置或修改上游仓库。
- 用固定流水线覆盖所有研究、教学、写作及实验性 skills。
- 修改 Orca 内核、发送外部沟通、使用真实客户数据或付费操作。
- 自动将复盘/架构候选变成已授权开发，自动解决产品决策。
- 在本轮计划交付中实施脚本、创建 Run、发布远端票图或合并变更。

## Further Notes

研究固定的上游提交见研究文档；实际执行必须重新核对所安装 skill 和 Orca 版本。官方 skill 原义、宿主能力和本项目适配须分别说明。前期未提交修订只是候选基线，实施前以实际 diff 逐项核对，不把它们当已验收里程碑。

本规格不要求新增付费设施；确定性测试可在临时文件和隔离仓库执行。真实演练资源、消息和过程记录按本项目生命周期处理；自动化测试禁止消费真实用户邮箱。
