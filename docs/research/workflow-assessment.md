# 通道与流程评估

评估日期：2026-11-08；基线 `51d3cb2`。证据及版本见 [Matt Pocock skills](matt-pocock-skills.md) 和 [Orca 机制](orca-mechanisms.md)。这是规则与工具契约评估，不是历史 Run 审计；Orca 未做端到端消息实验。

补充调查：上游完整路由、命名及上下文策略见 [上游 skill 全景](upstream-skill-map.md)。原评估未覆盖 `grill-me` 包装器、`ask-matt` 路由和 wayfinder 的完整生命周期，以下为进一步审计后的修正。

## 入口与通道

先判断需要解决的问题与交付终点，再判断澄清、规划或实施的入口；通道是执行路由，不是需求已经清楚的证明。上游建议改动前使用 grill，本项目保留已充分明确的小修复直接实施的适配，但要求写出目标、范围、验收和关键取舍依据；出现未决取舍或用户要求 grill 就进入 grill。已有 spec 或票须核实其适用性，不能仅因文件存在便跳过对齐。讨论类仍留 A，规划或实施仍走 B/C；有新证据时重新路由。

Orca 的 Task spec 是委派说明，产品 spec 是对需求与方案的产物，两者不互为前提。可以先以 Task spec 委派 `grill-with-docs`，携带用户原话、已知事实和问题，通过 ask/reply 把决策交还用户。普通 ask 的调用等待行为与逻辑上的待决依赖不同。

## 阶段与门禁

| 阶段 | 评估与适配 |
| --- | --- |
| grill | 上游是访谈加领域建模；用户回答决策、确认共同理解。G-docs 应验对齐和记录，术语文件及 ADR 按需产生，而不是强求模板和固定文件名。 |
| to-spec | 综合已有上下文并核对测试 seam；不要用它补做整场访谈。用户已明确决定可复用，变化时核实。 |
| to-tickets | 核对纵向切片、粒度和真实阻塞关系；上游允许从计划或对话进入。本项目的完整长程实施选择以 spec 和已验票图为前提，是更严格的本项目政策。 |
| implement / implement-spec | 单票和完整票图是不同入口。后者拥有 integration branch、隔离 implementer、依赖 frontier 和一次集成 review；Orca 不替代业务验收。 |
| review / 合并 | 保留证据和授权检查；已授权的可逆执行动作不必重新获取相同授权。 |

## 本次修改与后续验证

本次收紧入口证据，修正 grill 门禁、setup 验收的分流和 ask 描述，并限定续跑输出的解释范围。`chain.py` 仍然计算固定的五位置序列：它不保存本 Run 实际选择的入口、适用门禁与交付终点，不能独立证明非完整链条已完成。修改其数据模型需要先设计兼容既有台账、跨 Run 复用证据及缺失/撤销证据的语义；本次不将一条警告包装成已解决的脚本能力。

后续应在隔离环境做一次真实 grill → ask/reply → 用户确认的 Orca 演练，核验版本、问题轮次、上下文指针、唤醒及恢复证据；再用已有 spec、直接小修复、只交付设计和完整票图四种场景检验路由与续跑。实际历史是否跳过 grill，需要以每次 Run 的任务、消息、用户确认和台账交叉审计，不能由此报告推定。

## 深入审计后补充

| 发现 | 本次处理 / 尚待处理 |
| --- | --- |
| `grill-me`、`wayfinder` 和 `prototype` 缺少明确派活映射；只读取 `grill-with-docs` 包装器不能证明依赖运行 | 增补路由、依赖解析和跨上下文决策证据；宿主对用户调用入口的限制仍须遵守。 |
| G-wayfinder 用地图全部完成的条件验收建图，遗漏逐票生命周期；错误排除前置 task，强制原生边与 tracker fallback 相冲突 | 分开建图、逐票和地图完成验收，明确四类票、人类参与、会话边界与 fallback。 |
| 通用实施 PR 契约不适合研究与原型的一次性分支 | 在路由中注明按授权交付终点选择临时分支和上下文指针。 |
| 上游建议访谈、规格和拆票尽量留在同一上下文；项目跨 worker 增加决定丢失风险 | 增补原话、约束和依赖的交接要求；尚未用真实 Orca Run 验证保真度。 |
| `chain.py exit-check` 把 `##` 当票块，不能正确理解上游一票一文件和 issue 分节；`to-spec` 的验收章节及测试档是本项目增补 | 已明确禁止将现有检查结果用于上述上游格式；脚本尚未支持这些格式，需先定义输入类型和兼容策略并用真实格式样例验证。 |
| 固定五位置 resume 不能表达 wayfinder 的建图、逐票与地图完成 | 不把 resume 作为地图权威；以 tracker、票状态和实际用户决定核验。状态模型改造仍待设计。 |

不能把以上文本修订视为流程行为已经端到端验证。应使用实际 chart、HITL 逐票、AFK 研究、prototype 和 tracker fallback 场景测试，同时验证不同宿主对 user-invoked wrapper 的支持。
