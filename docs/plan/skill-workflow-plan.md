# 工作流重构详细实施计划

状态：规划交付，未启动实施。需求与行为正本：[spec](../design/skill-workflow-spec.md)。

## 1. 起点与交付边界

当前工作树已有前期未提交的双语 skill/README 修订和研究文档；这些作为候选输入，不标为已验证实现。实施前记录基线提交、工作树 diff、上游 skill 版本、Orca 版本与能力。先保护现有修改，再采用用户选择的隔离分支/Orca 工作区方式推进。

本轮交付 spec、分析、任务与审阅结果；下一轮实施范围是将这些契约变成可验证的双语工作流、脚本及证据。GitHub issue 发布、PR 和合并各按实际用户授权执行。测试 seam 和任务切分在审阅本计划时可调整，不预先声称用户已经批准技术细节。

## 3. 实施阶段

### 阶段一：先校准入口与规划上下文

WF-01 读取原版 ask-matt 及每个实际选中的 skill，按“条件→输入→动作→完成证据→回流”建立单一权威路由。A/B/C 只保留交付/监督意义；合并现有重复路由段落。核对 wrapper 依赖、用户调用限制、setup 策略及上游适配说明。

WF-02 接着明确同一规划会话优先、何时拆 session、何时用 handoff、Task spec 与产品 spec 的边界。用带数值、否定要求、既定决定和未决问题的固定对话样本做保真评测。不得仅根据“生成了 handoff 文件”判通过。

阶段验收：新需求、无目录访谈、已有有效 spec、过期 spec、明确小修复、宿主缺 skill、包装器依赖缺失均有明确路径。新取舍会触发澄清；原始决定可追溯。

### 阶段二：补齐决策地图和支线

WF-03 将 chart、work、map-complete 分开；覆盖无 fog 退出、真实认领、先建票再连边、resolution/关闭/索引、动态 fog 更新。分别跑 research、prototype、grilling、task 四类样例；核对 HITL 与 AFK、一次性产物和 PR 策略。

问卷接收人未答、向导未完成都保持明确阻塞，不替人填答。返回结果进入原问题而非自动进入实施。地图全部收敛后给 to-spec 或有依据的小工作交接。

### 阶段三：使流程状态与脚本一致

WF-04 先落显式流程数据和台账兼容合同，使用现有 ledger 的公开入口验证；决定 schema 版本及升级方式并更新文档。将节点身份、验收 attempt、产物版本、导入来源和失效依赖放在可核验记录中。

WF-05 消费该合同改造续跑，保留旧调用但标明 legacy；旧账本不自动转换成完整新流程。测试直接实施、design-only、单票、整图、wayfinder、前次产物复用、旧成功/新失败、回滚、失效传播与授权终点。

WF-06 对产物检查提供明确格式边界，以原版模板样例驱动修复。错误输出定位到真实票或章节，不能把 issue 的分节当成多张票；原生检查和调度增补分别报告。

### 阶段四：治理、集成和真实验证

WF-07 统一 triage、architecture、retro 等入口与回流；改动两个语言包及相关 README、scenario、计数和引用。用真实流程记录、台账和票文件穿透相邻模块，运行行为评测；一个字符串检查不能证明 agent 实际执行了交互。

WF-08 在隔离测试仓库/可清理 tracker 中进行真实 Orca 演练，不消费现有用户邮箱。记录版本、Run/Task/Dispatch 对应关系、消息、产物、验收、资源生命周期及已知能力限制，发布材料去敏。未能运行的场景记未验证并说明对发布的影响，不用 mock 替代真实证据。

## 4. 并行和隔离安排

默认按表推进。WF-03 与 WF-06 在 WF-02 后可并行，但其文档若触碰相同 spec/引用文件则串行合入。WF-05 与 WF-06 都可能修改 chain 模块、两语言副本及测试，默认串行；除非提前分离职责并证明路径不重叠。WF-04 依赖 WF-03，因为必须先明确 wayfinder 阶段合同。

实施若采用完整票图长程 worker，integration branch 是唯一集成点；嵌套执行者从当前集成 tip 起步，依赖按合入集成分支判断。不得一边依赖未合入提交、一边从无关主分支开始。具体执行拓扑在正式启动时根据用户指定方式和现场能力确定。

## 5. 验证与 review

每项任务先复现其目标缺陷或给出可失败场景，再验证改动后的公共行为。代码任务运行受影响测试；整合后运行 CONTRIBUTING 指定的全量 unittest 及 CI 矩阵。遵循项目当前 Python/OS 支持范围，不在本计划中固定未来版本。

独立 verify 审阅 spec 对齐、真实调用连接、旧数据兼容、去敏与双语语义。blocking 修复后复验；不能以修改预期值掩盖行为错误。门禁最终需要同时有确定性测试、agent 场景评测和指定真实 Orca 演练证据。

建议新增场景至少包括：新需求先澄清；无目录 grill-me；有目录 docs wrapper 依赖；明确小修复入口依据；规划上下文保真；chart 有未决票仍成功；work HITL 真答；research 并行；task 前置动作；无 fog 退出；fallback blocker；空 frontier 非完成；问卷和 wizard 返回；retro 仅候选；架构候选选择；旧账本 legacy；新失败覆盖旧尝试；产物变更失效；单票格式与 issue 章节；规格原生与调度附加项；只设计终点；失联/重复消息恢复。

## 6. 兼容、风险与回退

| 风险 | 控制与回退 |
| --- | --- |
| 旧台账被错误解释 | 保留文件，显式 legacy，不推断缺失的入口与确认；兼容样本纳入回归。 |
| 规划上下文过长或交接丢决定 | 阶段边界压缩/交接，逐条追溯用户约束；无法核验时不继续依赖工作。 |
| 上游或 Orca 能力变化 | 记录版本，运行前现场加载；缺能力给明确报告，不自动替换 agent/入口。 |
| 文本变长导致路由不可靠 | 主入口只保留必要判据，按分支引用；删除重复规则并做行为评测。 |
| 临时分支误并入产品 | spec/票明确交付形态，验收检查 branch 和 PR 目标，按生命周期清理。 |
| 双语语义漂移 | 同任务修改并审阅两个包，脚本字节检查，等价场景对照。 |
| 部分实现上线而数据不兼容 | 每个里程碑可回退到明确版本；新格式不破坏旧读取，回退前保留新记录和证据，不删除历史。 |

## 7. 完成定义

WF-01—08 均有独立验收记录，AC01—15 均有对应证据；没有未知的流程语义或未解释的兼容错误；双语与 CI 回归通过；指定真实演练完成。之后按用户授权交付开放 PR 或合并，收口报告列实际验证范围、剩余限制和回退方式。

本轮计划和 spec 的完成只证明方案可审阅，不意味着上述实施任务已完成。
